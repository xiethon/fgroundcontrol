# 代码提交规则

- 提交、推送按用户要求执行，不自动推送或合并。
- 操作前检查分支、工作区和差异；保留用户已有改动。
- 一次提交只解决一件事；按文件暂存，检查暂存差异，避免夹带无关内容。
- 提交格式：`type(scope): 简述`；type 使用 feat、fix、refactor、docs、test、build、chore。
- 标题说明具体变化；复杂修改补充原因与验证结果，不写空泛描述。
- 提交前完成相关检查；不提交密钥、构建产物、设备日志或本地配置。
- `main` 为受保护的集成主分支，保持可构建；通过分支审查与验证后合入，不直接推送或强推。
- 实施前从 `main` 新建并切换到开发分支 `feat/<阶段>-<主题>`，完成后合回 `main`；不在 `main` 直接开发。
- 发布分支使用 `release/<版本>`，从确认的发布基线创建；冻结后只接收发布修复和版本文档，不加入新功能。
- 发布前完成验收，修复同步回 `main`。
- 版本采用 `MAJOR.MINOR.PATCH`：不兼容变更升主版本，兼容功能升次版本，修复升补丁版本；预发布使用 `-alpha.N`、`-beta.N` 或 `-rc.N`。
- 发布使用附注标签 `v<版本>`，指向已验收的发布提交；标签、应用版本和发布说明一致。已发布标签不得移动或覆盖，纠错发布新版本。
- 普通 Bug 使用 `fix/<编号或主题>`，从目标修复分支创建，验证后合回原分支。
- 已发布版本紧急修复使用 `hotfix/<版本>-<主题>`，从对应发布标签创建；验证后发布补丁版本，并同步到 `main` 及受影响的发布分支。
- 跨分支同步优先挑选明确的修复提交，避免带入未发布功能；记录来源提交并处理冲突后重新验证。
- 分支使命结束后删除本地和远程分支，并清理远程跟踪引用；`main` 保留，版本历史由标签保留。
- 删除前确认改动已合入或同步、无独有待保留提交、无未提交改动及关联 worktree；发布分支需确认不再维护。不满足条件时先处理，不强制删除。
- 未明确授权不执行强推、硬重置、丢弃改动或改写已有提交。
- 完成后报告提交号、摘要和验证结果；推送失败如实说明。
